## 4.1 전체 구조

덱은 PC와 연결돼 **PC 상태를 표시하고 PC 작업을 제어한다.** 연결되는 PC를 **호스트**라 부른다.

```
  PC (호스트)                                  덱 (토스 프론트)
┌──────────────────────┐                  ┌─────────────────────────────────┐
│ toss-connector            │   TCP 7879       │ tossd (데몬)       UI (QML)     │
│  미디어·리소스·명령 ─┼─── 상태 ───────▶ │  hosts/ ────────────▶ 위젯      │
│  권한 검사(trust) ◀──┼── 액션(action) ──┼─          ◀─action── 버튼·노브 │
└──────────────────────┘  USB·이더넷·Wi-Fi └─────────────────────────────────┘
        연결은 PC가 연다. 수립된 뒤에는 양쪽이 자유롭게 송신한다.
```

| 모듈/컴포넌트 | 위치 | 역할 |
|---|---|---|
| 프로토콜 `toss-proto` | `src/app/proto/` | 메시지 포맷(`src/lib.rs`), 키와 암호화(`src/secure.rs`). 덱 데몬과 호스트 커넥터가 공용 |
| 호스트 커넥터 `toss-connector` | `src/app/host/` | PC에서 동작. 페어링된 덱에 접속해 상태를 보내고 허용 범위 내 액션을 실행. 웹 콘솔도 제공(`console/`) |
| 리소스 측정 `toss-meter` | `src/app/meter/` | CPU, 메모리, GPU, 디스크, 네트워크, 온도 측정. 덱(자체 리소스)과 호스트(PC 리소스)가 공용 |
| NixOS 패키지·모듈 | `nix/toss-connector.nix`, `nix/nixos-module.nix` | 호스트 커넥터 설치 및 자동 실행. 권한과 명령을 설정으로 선언 가능 |
| 덱 측 호스트 계층 | `src/app/tossd/src/hosts/` | 호스트 연결 수락. 페어링, 호스트 상태를 UI로 전달, UI 액션을 호스트로 전달 (4.11절) |
| 덱 UI | `src/app/ui/shell/DevicesPage`, `DevicePage`, `PairPage`, `src/app/ui/widgets/MediaWidget`, `MeterWidget`, `CommandBase`, `CommandWidget`, `CommandSwitchWidget`, `CommandSteppedWidget`, `CommandLinearWidget` | 설정의 `Paired devices`(목록, 페어링, 삭제 — 삭제는 확인 다이얼로그) 및 호스트 연동 위젯(미디어 제어, 리소스 미터, 명령 버튼, 명령 스위치, 단계 노브, 연속 노브. 명령 위젯 4종 공통 베이스는 `CommandBase`) |

### 요구사항과 설계 결정

| 요구사항 | 설계 결정 |
|---|---|
| 리눅스, Windows, macOS 모두 지원 | 호스트 커넥터는 단일 Rust 코드베이스로 작성하고, OS 종속 부분만 모듈 내부에서 분기(현재는 리눅스만 구현) |
| 실시간성(재생 정보 즉시 반영, 빠른 조작 응답) | 상시 연결을 유지한 채 양쪽이 필요할 때 바로 푸시. 요청-응답 방식 아님. **상태는 이벤트 발생 시, 또는 값이 바뀔 때만 전송**(4.7절) |
| USB와 LAN(이더넷, Wi-Fi) 모두 지원 | 모든 경로를 IP 기반으로 통합. USB도 네트워크(USB 이더넷)로 취급하므로 전송 계층을 경로별로 구현할 필요 없음 |
| 어느 경로로 붙어도 동일 기기로 식별 | IP 주소가 아니라 **공개키가 신원(ID)** |
| 한 경로가 끊기면 다른 경로로 전환 | 호스트가 덱의 여러 IP를 기억해 순차 접속 시도(현재는 재연결 방식, 4.8절) |
| 덱 1대에 PC 여러 대 동시 연결 | 덱이 다중 호스트 동시 접속 수락 |
| 기본 보안 | 페어링된 공개키만 수락하고 전 구간 암호화. USB·LAN 구분 없이 동일 적용 |
| PC가 덱 권한을 세밀하게 제어 가능 | PC 측에서 덱별로 허용 권한을 지정하고 허용된 작업만 실행(4.5절) |

**연결은 호스트(PC)가 먼저 연다.** PC에서 포트를 열면 Windows/macOS 방화벽에 걸리기 쉽기 때문이다. 덱은 모든 인터페이스에서 `7879` 포트를 열고 대기한다.

### 용어 정리

| 용어 | 의미 |
|---|---|
| 덱 | 토스 프론트. 데몬 `tossd`가 연결을 수락 |
| 호스트 | 덱과 연결되는 PC. `toss-connector`가 동작 |
| 신원, ID | 각 기기의 X25519 공개키(16진수 64자) |
| 페어링 | 서로의 공개키를 신뢰 목록에 저장하는 절차 |
| 권한(`caps`, `perms`) | 호스트가 해당 덱에 허용한 기능 범위. PC 사용자가 지정 |
| 상태 | 호스트가 덱으로 푸시하는 데이터: 재생 중인 곡과 앨범 아트, 등록된 명령 목록과 스위치·노브 값, 메트릭 목록과 수치 |
| 액션(`action`) | 덱이 호스트에 요청하는 작업: 미디어 제어, 등록된 명령 실행 및 값 설정 |
| 구독(`watch`) | 덱이 현재 표시 중인 메트릭을 호스트에 알리는 메시지. 호스트는 구독된 항목만 측정 |
| 관리형 설정(managed config) | NixOS 모듈이 고정한 권한과 명령(`/etc/toss-connector/managed.json`). 사용자 설정 위에 덮어씌워짐 |

## 4.2 프레이밍

TCP 위에서 **"길이(2바이트 빅 엔디안) + 페이로드"** 프레임을 연속 송수신한다.

| 단계 | 내용 |
|---|---|
| 연결 직후 3회 | Noise 핸드셰이크 메시지(4.3절). 호스트 → 덱 → 호스트 순 |
| 핸드셰이크 이후 | AEAD 암호문. 복호화하면 UTF-8 JSON 1건이며 `"t"` 필드로 타입 구분. 예: `{"t":"action","id":7,"name":"media.next"}` |

- 단일 메시지는 암호문 기준 65535바이트가 상한이다(평문은 MAC 16바이트만큼 작음). 이보다 큰 바이너리(앨범 아트 등)는 청크로 분할해 보낸다(4.6절 `blob`).
- **알 수 없는 메시지 타입은 무시한다.** 한쪽만 신버전이어도 연결이 끊어지지 않는다. JSON 파싱에 실패한 메시지도 무시한다.
- 복호화에 실패하면 즉시 연결을 종료한다.
- 프로토콜 버전(`PROTO_VERSION`, 현재 `3`)은 `hello`에 실어 교환한다. 버전이 다르면 연결을 닫는다(덱은 종료 전 자신의 버전이 담긴 `hello`를 `denied` 상태로 먼저 보내 호스트가 사유를 알 수 있게 한다). 메시지를 **추가**할 때는 버전을 올리지 않고(알 수 없는 메시지는 무시되므로), 기존 메시지의 시맨틱을 변경할 때 올린다. `3`에서 `media` 재생 위치 기준이 "전송 시점 기준 위치"로 바뀌었다.
- 핸드셰이크에 바인딩하는 프롤로그/프로토콜 이름(`tossfront-deck/2`, 4.3절)의 숫자는 키 교환·프레이밍 계층 버전이다. JSON 메시지 프로토콜 버전과는 별개로 관리한다.

## 4.3 신원 및 암호화

- 각 기기는 **X25519 키 쌍 1개**를 가진다. 최초 실행 시 생성해 저장한다. **공개키 자체가 기기 ID다.** USB로 붙든 이더넷·Wi-Fi로 붙든 공개키가 같으면 같은 기기다.
- 연결 시 Noise XX 패턴(`Noise_XX_25519_ChaChaPoly_BLAKE2s`)으로 상호 공개키를 교환한다. 공개키 자체도 암호화돼 전달된다. 이후 모든 메시지는 암호화되며 변조 시 복호화에 실패한다.
- 핸드셰이크에 프로토콜 식별자(`tossfront-deck/2`)를 바인딩한다. 다른 프로토콜을 쓰는 상대와는 핸드셰이크 자체가 실패한다.
- **암호 계층은 상대의 공개키까지만 보증한다.** Noise 계층은 "상대 공개키가 X이다"까지만 보장하며, 해당 키를 수락할지(페어링 여부)는 상위 애플리케이션 계층이 판단한다.
- **6자리 검증 코드**: 핸드셰이크 해시에서 추출한다(앞 4바이트를 u32로 읽어 `1_000_000`으로 나눈 나머지, `"123 456"` 형식). 세션마다 달라지며 양쪽에서 동일하게 산출된다. 중간자 공격(MITM)으로 양쪽과 각각 세션을 맺으면 핸드셰이크 해시가 달라져 코드가 일치하지 않는다. 페어링 시 사용자가 육안으로 이 코드를 대조한다.
- 암호 구현은 순수 Rust만 사용한다(`snow` 기본 피처를 끄고 필요한 알고리즘만 활성화). 기본 피처는 C·어셈블리 기반 `ring`을 끌고 와서 기기용 크로스 빌드가 깨진다.

## 4.4 페어링

**페어링은 서로의 공개키를 신뢰 목록에 저장하는 절차다. 페어링된 피어만 연결을 수락한다 — USB든 LAN이든 예외 없다.** USB로 연결했다고 자동으로 신뢰하지 않는다.

### 페어링 절차

1. 덱: 설정 버튼 → `Paired devices` → `PAIR NEW DEVICE`. 페어링 모드가 켜지고(2분), PC에서 실행할 명령어가 덱 IP별(USB, 이더넷, Wi-Fi)로 표시된다.
2. PC: `toss-connector pair`(USB 연결 시) 또는 `toss-connector pair --deck <덱 IP>`(LAN).
3. 덱 화면과 PC 터미널에 **동일한 6자리 숫자**가 뜬다.
4. 숫자가 같으면 덱에서 `ACCEPT`를 누르고 PC에서 `y`를 입력한다. 순서는 무관하며 **양쪽 모두 확인해야** 완료된다.
5. 이후에는 `toss-connector`만 실행하면 된다.

페어링 해제: 덱은 설정 → `Paired devices` → 대상 기기 → `FORGET`. PC는 `toss-connector forget <키 접두사>`. 한쪽에서만 삭제하면 서로 연결되지 않는다. **PC에서만 삭제했다면 덱에서도 삭제해야 재페어링할 수 있다**(`toss-connector pair`가 이를 안내한다). 덱에서만 삭제했다면 그대로 다시 페어링하면 된다.

### 메시지 교환 흐름

```
호스트                                   덱
  │── 핸드셰이크 (서로의 키, 검증 코드) ──│
  │── hello {pair: true} ───────────────▶│  페어링 모드인지? 다른 호스트와 진행 중인지?
  │◀── hello {status: "pairing"} ────────│  화면에 호스트명과 검증 코드 표시
  │    (양쪽 사용자가 숫자를 대조)        │
  │── pair_confirm ─────────────────────▶│  호스트 측 사용자 확인 완료
  │                                      │  덱 측 사용자 ACCEPT 탭
  │◀── paired ───────────────────────────│  덱이 호스트 키 저장 완료
  │  (호스트가 덱 키를 저장하고 연결 종료)│
```

| 덱이 `hello`로 회신하는 `status` | 의미 | 후속 동작 |
|---|---|---|
| `paired` | 이미 페어링된 호스트 | 즉시 정상 세션 시작. 단, 호스트가 페어링 요청(`pair: true`)으로 온 경우에는 상태만 알리고 세션을 시작하지 않으며 기존 동작 연결은 건드리지 않음 |
| `pairing` | 페어링 절차 시작 | 위 흐름 진행 |
| `denied` | 수락 불가 | 이어서 `denied`(사유)를 보내고 연결 종료. 이 `hello`에는 덱 IP(`addrs`)와 웨이크업 주소(`wake`)를 실어 보내지 않음 — 미등록 피어에게 정보 노출 방지. 프로토콜 버전 불일치로 닫을 때도 이 `hello`만 전송(`proto` 필드로 버전 안내) |

| `denied` 사유 | 의미 |
|---|---|
| `not_paired` | 미등록 상태이고 덱이 페어링 모드가 아님(또는 호스트가 페어링을 요청하지 않음) |
| `busy` | 다른 호스트와 페어링 진행 중. 한 번에 1대만 가능 |
| `rejected` | 덱 사용자가 거절했거나 페어링 화면을 벗어나 모드가 꺼짐 |
| `timeout` | 페어링 모드 제한 시간 만료(2분) |
| `forgotten` | 덱에서 해당 호스트 페어링을 삭제함(연결 중이던 세션에 알린 뒤 종료) |

- 페어링 화면을 벗어나거나 설정 패널을 닫으면 페어링 모드가 꺼진다.
- 페어링 전용 연결에서는 호스트가 어떤 권한도 부여하지 않는다(`caps` 빈 배열). 페어링이 완료되면 해당 연결을 닫고 상시 실행 중인 커넥터가 정상 재연결한다.
- 호스트는 로컬 사용자가 숫자를 확인하기 전에(`pair_confirm` 전송 전) `paired`를 수신해도 무시한다. 덱을 저장하지 않고 종료한다(상대가 진짜 덱인지는 숫자 대조 후에만 신뢰할 수 있기 때문).
- 덱 측은 호스트가 연결을 끊지 않으면 페어링이 끝난 연결을 그대로 일반 세션으로 이어서 쓸 수 있도록 구현돼 있다.
- **덱 수락은 화면에 표시됐던 검증 코드에 바인딩된다.** UI는 `ACCEPT` 탭 시 당시 코드를 데몬에 함께 넘기며, 데몬은 현재 후보의 코드와 다르면 수락을 버린다. 탭하는 찰나에 후보가 다른 호스트로 바뀌어도 사용자가 확인하지 않은 호스트가 수락되는 일을 막는다.
- 후보 슬롯은 페어링 종료 즉시(수락·취소 무관) 비워진다. 호스트가 `paired` 수신 직후 연결을 닫아도 다음 페어링을 방해하지 않는다. 덱은 호스트 키를 파일에 저장한 뒤에 `paired`를 보낸다.
- 덱은 호스트가 보낸 이름과 OS 문자열을 정제해 사용한다: 제어 문자를 제거하고 이름은 64자, OS는 32자로 자른다. UI와 덱 로그에 그대로 노출되기 때문이다. 허용 권한(`caps`)도 유효한 식별자 형태(짧은 ASCII 그래픽 문자)만 남긴다.

## 4.5 신뢰 경계: 호스트가 덱에 허용하는 권한

페어링은 "상대 덱이 맞다"는 신원만 검증한다. **해당 덱에 어떤 기능을 내줄지는 PC 측에서 덱별로 지정한다.** 덱은 허용된 목록을 조회만 할 수 있고 변경할 수는 없다.

| 권한 | 허용 시 기능 | 기본값 |
|---|---|---|
| `media.info` | 재생 중인 곡 제목·아티스트·앨범·진행 상태를 덱으로 전송 | 허용 |
| `media.control` | 덱에서 재생/일시정지, 트랙 이동, 시크, 반복·셔플 제어 가능 | 허용 |
| `resource.info` | PC 리소스 사용량(CPU, 메모리, GPU, 디스크, 네트워크, 온도)을 덱으로 전송. 덱의 리소스 미터 위젯이 구독 중인 항목만 측정(4.6절 "리소스 모니터링") | 허용 |
| `command.run` | PC에 **미리 등록된** 명령을 덱에서 실행하고, 등록된 스위치·노브 상태를 조회·변경 가능(4.6절 "명령") | **거부** |

### 동작 규칙

- **호스트는 위 표에 정의된 권한만 인정한다.** 덱이 보낸 액션마다 필요한 권한이 매핑돼 있다(`toss_proto::action_cap`). 해당 권한이 꺼져 있으면 실행하지 않고 `result`의 `error`를 `not_allowed`로 회신한다.
- **어떤 권한이 필요한지 알 수 없는 액션은 거부한다.** 현재 버전이 모르는 액션을 덱이 요청해도 실행하지 않는다.
- **별도로 설정하지 않은 권한은 기본값을 따른다.** 사용자가 명시적으로 바꾼 값만 파일에 기록한다. 현재 버전이 모르는 권한 이름이 파일에 켜져 있다고 적혀 있어도 비활성으로 취급한다.
- 재생 정보는 `media.info`가 켜져 있을 때만 플레이어를 조회해 전송한다. 권한을 끄면 빈 상태(`null`)를 1회 보내 덱 화면에서 지운다.
- 호스트는 켜져 있고 **실제로 사용 가능한 기능**만 덱에 알린다(`hello`의 `caps`). 미디어 플레이어 연동이 불가능한 환경에서는 `media.info`/`media.control`이 켜져 있어도 알리지 않는다.
- **연결 중 권한을 바꾸면 곧 반영된다.** 실행 중인 `toss-connector`는 설정 파일(`decks.json`) 변경을 0.5초마다 감시하고, 액션을 실행하기 직전에도 최신 설정을 다시 읽어 검증한다(방금 끈 권한으로 액션이 통과되는 경쟁 조건 방지). 재시작할 필요가 없다. 변경된 권한 목록은 덱에도 알린다(`caps` 메시지).
- **PC에서 페어링을 삭제하면** 연결 중이던 세션도 즉시 끊는다.
- **페어링되지 않은 피어에는 어떤 정보도 보내지 않는다.** 키 교환으로 상대 신원을 확인한 뒤에야 `hello`(이름, OS, 허용 권한)를 보낸다.
- 거부된 액션은 호스트 로그에 남는다(`덱 요청 거부됨 (…)`).
- **PC 시스템을 변경하는 권한(명령 실행, 키 입력 등)은 기본값이 거부다.** 사용자가 덱마다 명시적으로 허용해야 한다. `command.run`이 여기에 해당한다.

### 권한 변경 방법

웹 콘솔에서 덱별로 토글할 수 있고(`toss-connector console`, 4.10절 "웹 콘솔"), CLI로도 제어된다.

```bash
toss-connector trust                    # 덱별 허용 권한 조회
toss-connector deny media.control       # 거부 (페어링된 덱이 1대면 덱 ID 생략 가능)
toss-connector allow a1b2 media.control # 허용 (덱이 여러 대면 키 접두사 지정)
toss-connector deny all                 # 전체 거부 (페어링은 유지)
```

모든 권한을 한 번에 여는 `allow all`은 두지 않았다(향후 추가될 고위험 권한까지 실수로 허용하는 것을 막기 위함).

NixOS에서는 시스템 설정으로 권한을 고정할 수도 있다(`programs.toss-connector.config`, 4.10절 "NixOS에서 권한·명령 고정"). 고정된 권한은 CLI나 콘솔에서 바꿀 수 없고 덱에도 고정된 값이 전달된다.

### 덱 UI에서의 표시

- 미디어 위젯: `media.control`이 없으면 버튼이 비활성화된다. `media.info`가 없으면 `Not shared`가 표시된다.
- 리소스 미터: `resource.info`가 없으면 해당 PC 행이 흐려지고 수치 자리에 `--`가 뜬다.
- 명령 위젯(버튼, 스위치, 노브): `command.run`이 없으면 흐려지고 눌리지 않는다. 위젯 추가 메뉴에도 해당 PC의 명령이 나오지 않는다.
- 설정 → `Paired devices` → 대상 기기의 `Allows` 항목에서 현재 허용된 권한을 확인할 수 있다(연결 중일 때만). 변경은 PC에서만 가능하다.

### 웹 콘솔 인터페이스 참고

웹 콘솔(4.10절)은 CLI와 동일한 저장소·명령 체계를 쓴다. 권한 설정 UI를 추가로 구현할 때도 아래 구성 요소만 연동하면 된다:

| 필요한 기능 | 기존 구현 |
|---|---|
| 권한 목록, 이름, 설명, 기본값 | `src/app/host/src/trust.rs`의 `PERMISSIONS` 테이블 단일 정의. CLI도 이 테이블을 참조해 출력 |
| 덱별 설정 읽고 쓰기 | `src/app/host/src/store.rs`의 `Store::decks`(읽기), `Store::update`(해당 덱 항목만 수정) |
| 변경 시 곧 반영 | 실행 중인 프로세스가 `decks.json` 변경을 감지해 다시 로드. 설정 UI는 파일만 수정하면 됨(같은 프로세스든 별도 프로세스든 동일) |

## 4.6 메시지 스펙

### 호스트 → 덱 (`HostMsg`)

| 메시지 | 필드 | 의미 |
|---|---|---|
| `hello` | `proto`, `name`, `os`, `caps`, `pair` | 연결 직후 1회. 프로토콜 버전, 호스트명과 OS, 해당 덱에 허용된 권한, 페어링 요청 여부 |
| `caps` | `caps` | 연결 중 해당 덱의 허용 권한이 변경됨. 목록 전체를 교체 |
| `commands` | `commands`(`id`, `name`, `kind`, 종류에 따라 `steps` 또는 `min`·`max`·`step`) | 호스트에 등록된 명령 목록. `command.run` 허용 시에만 연결 직후 및 목록 변경마다 전체 전송. 실행 커맨드 문자열은 포함되지 않음. 단일 메시지 크기 상한을 넘기면 들어가는 만큼만 앞부분부터 잘라 전송 |
| `command_value` | `id`, `value`(모르면 `null`) | 상태를 가진 명령(스위치, 단계, 범위)의 현재 값. **값이 바뀐 경우에만** 전송(단 `commands` 전송 직후 초기값 1회와 덱이 값을 설정한 직후 재조회한 값은 변화가 없어도 전송). 스위치는 `0`/`1`, 단계는 인덱스(0부터), 범위는 수치 |
| `metrics` | `metrics`(`id`, `name`, `title`, `unit`, `max`, `decimals`) | 호스트에서 수집 가능한 메트릭 목록. `resource.info` 허용 시에만 연결 직후 및 변경 시 전체 전송. 권한을 끄면 빈 목록 전송 |
| `metric_values` | `values`(메트릭 ID → 값) | 메트릭 현재 값. **덱이 구독 요청한 항목 중 값이 바뀐 항목만** 전송(약 1초 주기) |
| `pair_confirm` | — | 호스트 측 사용자가 검증 코드를 확인함 |
| `media` | `media`(없으면 `null`) | 재생 정보. **이벤트 발생 시에만** 전체 전송: 곡 변경, 재생/일시정지/정지, 시크, 플레이어 생성·종료. 재생 중 경과 시간 갱신용으로는 보내지 않음 |
| `blob` | `id`, `mime`, `index`, `count`, `data` | 대용량 바이너리 청크(현재는 앨범 아트). 아래 "대용량 바이너리" 참고 |
| `result` | `id`, `ok`, `error` | 덱이 요청한 액션 결과. 미허용 권한이면 `error`는 `not_allowed`. 덱은 그 액션을 받은 호스트의 응답만 매칭함(다른 호스트가 같은 ID로 보낸 응답은 무시) |
| `sleep` | — | 덱 절전 진입 요청(`toss-connector sleep`). 덱은 `sleeping` 응답 후 슬립 진입 |
| `ping` | — | 연결 유지(keep-alive) |

### 덱 → 호스트 (`DeckMsg`)

| 메시지 | 필드 | 의미 |
|---|---|---|
| `hello` | `proto`, `name`, `status`, `addrs`, `wake` | `hello` 응답. 덱 이름, 수락 결과(4.4절), 덱 접속 가능 IP 목록, 절전 웨이크업용 주소(덱 Wi-Fi MAC). 거절 대상(`status`가 `denied`)에는 IP와 웨이크업 주소를 비워 보냄 |
| `sleeping` | `ok`, `reason` | `sleep` 응답. `ok`면 곧 슬립 진입. 실패 시 사유: `no_wifi`(Wi-Fi 미연결로 깨울 수단 없음), `unavailable` |
| `paired` | — | 페어링 완료 |
| `denied` | `reason` | 연결 거절. 직후 소켓 종료 |
| `action` | `id`, `name`, `args` | 액션 실행 요청. `id`는 `result`와 상관관계 매칭용 시퀀스 |
| `watch` | `metrics`(메트릭 ID 목록) | 덱이 현재 표시 중인 메트릭 목록. 호스트는 여기에 포함된 항목만 수집. 연결 직후 및 레이아웃 변경마다 전체 전송. 빈 배열이면 수집 중단 |
| `ping` | — | 연결 유지(keep-alive) |

### 재생 정보 (`media`)

| 필드 | 의미 |
|---|---|
| `player` | 플레이어 이름 (예: `spotify`) |
| `status` | `playing` / `paused` / `stopped` |
| `title`, `artist`, `album` | 트랙 정보. 아티스트가 여러 명이면 쉼표로 결합 |
| `length_ms` | 곡 길이(ms). 알 수 없으면 0 |
| `position_ms` | **이 메시지 전송 시점 기준** 재생 위치(ms). 수신 측은 `playing` 상태인 동안 여기서부터 자체 타이머로 진행 |
| `rate` | 재생 배속(보통 1.0). 수신 측은 이 배속으로 진행. **0이면 진행하지 않음** — 재생 위치를 제공하지 않는 플레이어의 경우 호스트가 0으로 전송 |
| `can_seek` | 시크 지원 여부 |
| `shuffle` | 셔플 활성 여부. **플레이어가 미지원이면 `null`** |
| `loop_mode` | 반복 모드: `none`, `playlist`(전체 반복), `track`(한 곡 반복). **플레이어가 미지원이면 `null`** |
| `art` | 앨범 아트 식별자(없으면 빈 문자열). 이미지 데이터는 동일 `id`의 `blob`으로 별도 전송 |
| `can_next`, `can_prev` | 다음·이전 트랙 이동 가능 여부 |

### 액션 (`action`의 `name`)

| 이름 | 동작 | 필요 권한 |
|---|---|---|
| `media.play_pause` | 재생/일시정지 토글 | `media.control` |
| `media.next` | 다음 곡 | `media.control` |
| `media.prev` | 이전 곡 | `media.control` |
| `media.seek` | 상대 시크. `args`: `{"offset_ms": -5000}`(현재 위치 기준 오프셋, 음수면 뒤로) | `media.control` |
| `media.shuffle` | 셔플 설정. `args`: `{"on": true}` | `media.control` |
| `media.loop` | 반복 모드 설정. `args`: `{"mode": "none" \| "playlist" \| "track"}` | `media.control` |
| `command.run` | 호스트에 등록된 명령 실행. `args`: `{"id": "<명령 ID>"}` | `command.run` |
| `command.set` | 호스트에 등록된 스위치·단계·범위 명령 값 설정. `args`: `{"id": "<명령 ID>", "value": 1}`(값 형식은 `command_value`와 동일) | `command.run` |

- **상태 전환 액션은 "토글하라"가 아니라 "이 값으로 설정하라"로 보낸다**(`on`, `mode`). 같은 메시지를 중복 수신해도 멱등성이 보장되며, 덱이 가진 상태가 약간 지연됐더라도 의도와 반대로 뒤집히지 않는다.
- 시크는 호스트가 목표 위치를 계산해 곡 범위 `[0, length_ms)` 내로 클램프한다(0 이전이면 0으로, 곡 끝을 넘기면 끝 직전으로 맞춰 다음 곡으로 넘어가지 않게 함).
- 덱 UI는 플레이어가 지원하지 않는 컨트롤을 비활성화한다(`can_seek`가 false거나 `shuffle`·`loop_mode`가 `null`인 경우). 예: Firefox는 셔플과 반복 모드를 제공하지 않는다.

### 명령 (`command.run`, `command.set`)

덱의 명령 위젯(버튼, 스위치, 노브)은 PC에서 명령을 실행한다. **실행 가능한 명령 정의는 PC에서만 관리한다.**

명령에는 종류(`kind`) 4가지가 있으며 종류마다 대응하는 덱 위젯이 다르다.

| 종류 | 설명 | 등록 항목 | 대응 덱 위젯 |
|---|---|---|---|
| `run` | 누르면 실행하는 단발성 명령(상태 없음) | 실행 셸 커맨드 1개 | 명령 버튼 |
| `switch` | 온/오프 토글 | 켜기 커맨드, 끄기 커맨드 | 명령 스위치(스위치 버튼) |
| `stepped` | 고정 단계 선택(예: off / passive / active / auto) | 단계 이름 목록 및 단계별 실행 커맨드 | 단계 노브 |
| `linear` | 연속 범위 값 조절(예: 0~100) | 범위, 단위, 값 설정 커맨드 | 연속 노브 |

**공통 동작**

- **명령은 PC에 등록해 둔다**(`toss-connector command add…`). 설정 디렉터리의 `commands.json`에 저장되며 해당 PC의 모든 덱이 같은 목록을 공유한다.
- **덱은 실제 셸 커맨드를 알지 못한다.** 호스트는 `command.run`을 허용한 덱에게만 목록을 보내며(`commands` 메시지), 여기에는 ID, 표시 이름, 종류, 메타데이터(단계 이름 목록, 범위·단위)만 담긴다. 덱 위젯은 ID만 저장했다가 액션에 실어 보낸다.
- **미등록 ID는 실행되지 않는다.** 덱이 raw 셸 커맨드를 보내도 ID 매칭이 실패하므로 실행될 수 없다. 따라서 덱이 탈취되더라도(덱의 SSH는 설정에서 닫지 않는 한 LAN에 열려 있다) PC에 미리 등록된 명령을 호출하거나 값을 조절하는 범위 이상으로는 실행되지 않는다.
- 실행은 사용자 셸을 사용한다(Unix `sh -c`, Windows `cmd /C`). 홈 디렉터리에서 `toss-connector`와 동일한 환경 변수로 실행하며 stdout/stderr는 버린다.
- 이름 수정 또는 삭제 시: ID가 불변이므로 이름만 바꾼 명령은 기존 위젯에서 계속 동작하고, 삭제한 명령을 가리키던 위젯은 흐려지며 비활성화된다.
- 덱 측 설정: 편집 모드에서 랙 빈 슬롯 `+` → `Command` → 위젯 종류(`Run`, `Switch`, `Stepped knob`, `Linear knob`) → PC·명령·라벨·색상 선택([03-userland-guide.md](03-userland-guide.md) 3.16절 "레이아웃 편집"). 목록에는 해당 위젯 종류와 호환되는 명령만 노출된다. PC 미연결 상태거나 권한·명령이 내려오지 않으면 위젯이 흐려진다.

**단발 실행 (`run`)**: `command.run` 액션으로 호출한다. **프로세스를 띄우기만 하고 종료를 기다리지 않는다**(앱 실행 용도가 많기 때문). `result`는 "스폰 성공 여부"만 반환한다. 덱 명령 버튼은 인디케이터가 없으며(무상태 버튼) 결과를 화면에 따로 띄우지 않고 실패 사유는 덱 데몬 로그에 남긴다. 실행한 명령 이름은 호스트 로그에 출력된다(`명령 실행: …`).

**값 설정 (`switch`, `stepped`, `linear`)**: `command.set` 액션으로 호출한다.

- **덱은 숫자만 보낸다**(스위치 `0`/`1`, 단계는 인덱스, 범위는 수치). 호스트가 대상 명령에 유효한 값인지 검증한다: 없는 단계 인덱스나 0/1 이외의 스위치 값은 거절하고, 범위 값은 `[min, max]` 범위와 단위에 맞춰 보정·스냅한다. 종류가 안 맞는 액션(스위치에 `command.run`, `run` 명령에 `command.set`)도 거절한다.
- **실제 실행되는 커맨드는 호스트 설정에서 꺼낸다.** 스위치는 on/off 커맨드, 단계는 해당 인덱스 커맨드를 실행한다. 범위·단계 공용 `--set` 커맨드 문자열에는 `{}` 플레이스홀더와 `TOSS_VALUE` 환경 변수로 값이 주입되며, 범위는 보정된 숫자가, 단계는 등록된 단계 이름이 들어간다. 덱이 보낸 문자열이 셸 커맨드에 삽입되는 일은 없다(`{}`에 들어가는 단계 이름도 영문자, 숫자, `. _ + -`만 허용).
- 값 설정 커맨드는 **직렬 큐에서 완료를 최대 5초까지 기다리며** 순차 실행한다. 같은 명령에 대기 중인 값이 쌓여 있으면 **가장 최신 값만 남기고 중간 값은 버린다**(노브 드래그 시 연속 요청 대응).
- `result`는 "큐에 적재하고 실행을 위임했다"는 뜻이다. 실제 변경 결과는 뒤이어 오는 `command_value`로 확인한다: 상태 조회 커맨드가 설정된 경우 쓰기 직후 재조회한 값은 이전과 같더라도 덱으로 보낸다(요청한 값이 반영되지 않았을 때 덱 UI를 실제 값으로 되돌리기 위함). 설정 값은 호스트 로그에 남고(`명령 값 설정: …`), 스폰 실패나 비정상 종료 시 에러도 남는다(`명령 …: 값을 설정하지 못했습니다: …`).

**상태 조회 (`command_value`)**: 현재 값은 PC가 파악하며 덱이 직접 질의하지 않는다.

- 등록 시 **상태 조회 커맨드**(`--state`)를 지정하면 호스트가 이를 `--every` 초(기본 2초)마다 주기적으로 실행해 **값이 바뀐 경우에만** 덱으로 전송한다. 값 설정 직후에는 즉시 1회, 0.4초 뒤 1회 추가로 조회한다. PC에서 직접 값을 바꾼 경우에도 이 메커니즘으로 덱에 반영된다(재생 정보와 동일한 원칙: 전송 시점 판단은 호스트가 맡는다, 4.7절).
- 출력 파싱 규칙: 스위치는 `on`/`1`/`true`/`yes`면 온(1), `off`/`0`/`false`/`no`면 오프(0), 그 외 출력(또는 빈 출력)이면 **종료 코드가 0일 때 온**(`pgrep -x obs` 같은 커맨드를 그대로 쓸 수 있음). 단계는 단계 이름(대소문자 무관) 또는 인덱스 번호로 매칭한다. 범위는 숫자(`%` 접미사 허용)를 파싱한다.
- 3초 타임아웃 안에 종료되지 않거나 파싱할 수 없으면 알 수 없음(`null`)으로 보낸다. 덱 노브는 `--`를 표시한다.
- `--state`가 없으면 호스트는 **마지막으로 설정한 값**만 기억해 보낸다. PC에서 직접 변경한 값은 감지하지 못하며 `toss-connector` 재시작 시 초기화된다.
- 상태 폴링은 해당 덱에 `command.run`이 허용돼 있는 동안에만 동작한다. 권한을 끄면 목록이 비고 덱 위젯도 비활성화된다.

```bash
toss-connector command add Terminal -- foot          # 단발 실행 명령 (버튼)
toss-connector command add-switch Mic \
    --on 'wpctl set-mute @DEFAULT_SOURCE@ 0' --off 'wpctl set-mute @DEFAULT_SOURCE@ 1' \
    --state '! wpctl get-volume @DEFAULT_SOURCE@ | grep -q MUTED'       # 스위치: 종료 코드 0 이 온
toss-connector command add-stepped Profile --set 'powerprofilesctl set {}' \
    --step power-saver --step balanced --step performance \
    --state 'powerprofilesctl get'                                      # 단계: {} 자리에 단계 이름
toss-connector command add-stepped Scene --step 'Game=obs-scene game' --step 'Chat=obs-scene chat'   # 단계별 개별 커맨드
toss-connector command add-linear Volume --max 100 --step 5 \
    --set 'wpctl set-volume @DEFAULT_SINK@ {}%' \
    --state "wpctl get-volume @DEFAULT_SINK@ | awk '{print int(\$2*100+0.5)}'"   # 범위: {} 자리에 숫자
toss-connector command list                          # 등록 목록 (ID, 종류, 이름, 커맨드)
toss-connector command run Terminal                  # PC 에서 직접 즉시 실행
toss-connector command set Volume 40                 # PC 에서 직접 값 설정 (on/off, 단계 이름, 숫자)
toss-connector command state Volume                  # 현재 상태 조회 테스트
toss-connector command remove Terminal               # 삭제
toss-connector allow command.run                     # 덱에 실행 권한 부여 (기본값 거부)
```

(위 커맨드들은 예시이며, 실기기 검증에서는 파일 읽기/쓰기 커맨드를 사용했다.)

### 리소스 모니터링 (`metrics`, `metric_values`, `watch`)

덱의 리소스 미터 위젯(앱 Resource monitor)이 PC 리소스 사용량을 표시한다. 덱 자체 리소스도 같은 위젯으로 볼 수 있으며, 그때는 덱 데몬이 직접 수집한다.

- **수집 가능한 항목 목록은 호스트가 알려 준다**(`metrics`). 덱은 그 목록에서 고르기만 한다. 메트릭마다 내부 식별자(`id`), 미터 옆 짧은 이름(`name`, 5자 이내), 선택 화면용 긴 이름(`title`), 단위(`unit`), 상한(`max`, 0이면 상한 없음 — 덱이 관측한 최댓값에 맞춰 스케일링), 소수 자릿수가 전달된다.
- **덱이 표시 중인 메트릭만 수집한다.** 덱은 레이아웃 내 리소스 미터 위젯들이 구독하는 메트릭을 호스트별로 모아 `watch`로 알린다. 호스트는 그 목록만 약 1초 간격으로 측정해 **값이 달라진 항목만** `metric_values`로 보낸다. 값은 표시 자릿수로 반올림해 비교하므로 화면상 차이가 없는 미세 변동은 전송하지 않는다. 덱이 아무것도 구독하지 않으면 호스트도 측정하지 않는다(다른 상태와 동일한 원칙: 전송 판단은 호스트가 담당).
- 단위 처리: `%`, `°C`, `GHz`, `W`, `RPM`은 수치 뒤에 그대로 붙인다. `B`(바이트)와 `B/s`(초당 바이트)는 덱이 크기에 맞게 KB·MB·GB로 변환한다. 빈 문자열은 무차원 수치다(로드 애버리지 등).
- 수집 코드는 덱과 PC가 동일한 크레이트를 사용한다(`src/app/meter`, `toss-meter`). 리눅스(`/proc`, `/sys`)만 지원하며 다른 OS 호스트는 `resource.info`를 제공하지 않는다.
- `resource.info`를 끄면 호스트가 빈 목록을 보내고, 덱 위젯은 흐려지며 `--`를 표시한다.

| 리소스 | ID | 출처 |
|---|---|---|
| CPU 사용률 (전체, 코어별) | `cpu`, `cpu.N` | `/proc/stat` |
| CPU 클럭(평균), 온도, 소비전력 | `cpu.freq`, `cpu.temp`, `cpu.power` | cpufreq, hwmon(`k10temp`·`coretemp`·`zenpower`, 없으면 thermal_zone), powercap(읽기 권한 있을 때만) |
| 로드 애버리지(1분) | `load` | `/proc/loadavg` |
| 메모리, 스왑 (사용량) | `mem`, `swap` | `/proc/meminfo` |
| GPU 사용률, VRAM, 온도, 전력, 팬 | `gpu`, `gpu.vram`, `gpu.temp`, `gpu.power`, `gpu.fan` (두 번째부터 `gpu2…`) | AMD: `/sys/class/drm` 및 hwmon. NVIDIA: `nvidia-smi`(있을 때). VRAM이 큰 GPU가 `gpu` |
| 디스크 읽기·쓰기 속도 (전체) | `disk.read`, `disk.write` | `/proc/diskstats` |
| 파일시스템별 사용량 | `fs.<이름>` | `/proc/mounts` 및 `statvfs`. 실제 블록 디바이스만, 최대 8개 |
| 네트워크 수신·송신 속도 (전체) | `net.down`, `net.up` | `/proc/net/dev`. 실제 물리 인터페이스가 있는 장치만 |
| SSD 온도 | `temp.ssd`, `temp.ssd2` | hwmon(`nvme`) |
| 팬 | `fan.N` | hwmon의 `fan*_input`(GPU 팬은 `gpu.fan`) |
| 배터리 | `battery` | `/sys/class/power_supply` |

시스템에 존재하는 장치만 목록에 나온다(GPU가 없으면 GPU 항목 없음). 현재 PC에서 잡히는 항목을 확인하려면 `cd src/app/meter && cargo run --example show`를 실행하면 된다.

### 대용량 바이너리 (`blob`)

단일 메시지 크기 제한을 넘는 데이터는 청크로 분할해 전송한다. 현재는 앨범 아트 전송에만 사용한다.

| 필드 | 의미 |
|---|---|
| `id` | 데이터 식별자. 용도는 참조하는 메시지로 매칭한다(`media`의 `art`가 이 ID를 가리킴) |
| `mime` | MIME 타입. 덱은 `image/jpeg`와 `image/png`만 수락 |
| `index`, `count` | 현재 청크 인덱스(0부터)와 전체 청크 수. 순서대로 전송 |
| `data` | 청크 페이로드(base64) |

- **마지막 청크를 제외한 원시 길이는 30000바이트(3의 배수)로 고정한다.** 그래야 수신 측이 base64를 디코딩하지 않고 청크 문자열을 그대로 이어 붙여도 유효한 전체 base64 문자열이 된다. 덱은 이렇게 결합해 QML `Image`로 바로 넘긴다.
- 청크 전송 사이에 다른 메시지(`ping`, `media` 등)가 끼어들 수 있다.
- 전체 크기 상한은 1MiB다. 순서가 어긋나거나, 미지원 MIME 타입이거나, 상한을 초과하면 덱은 버퍼를 폐기한다.

### 앨범 아트

- 플레이어가 이미지 URL을 제공한다(리눅스 MPRIS). 로컬 파일(`file://`, 예: Firefox)일 수도 있고 원격 URL(`https://`, 예: Spotify)일 수도 있다.
- **호스트가 이미지를 내려받아 축소해 보낸다.** 긴 변이 512px을 넘으면 비율을 유지해 512px 안으로 리사이징하고(작은 이미지는 확대하지 않음) JPEG로 재인코딩한다. 보통 40~80KB로 청크 2~3개 분량이다.
- **트랙 메타데이터가 먼저 가고 이미지는 뒤따라 간다.** `media`가 아트 ID를 실어 먼저 전송되고, 이미지 다운로드·인코딩이 끝나면 `blob`으로 전송된다. 그사이 덱은 아트 영역에 재생 상태 아이콘을 표시한다.
- ID는 이미지 URL에서 해싱해 만든다. 같은 URL이면 동일 이미지로 취급해 재전송하지 않는다(같은 앨범의 다음 곡 재생 시 등).
- 앨범 아트 전송은 `media.info` 권한에 종속된다. 권한을 끄면 전송하지 않고 덱도 보유 중이던 이미지를 비운다.
- 다운로드/디코딩에 실패하면(네트워크 끊김, 잘못된 이미지 등) 다음 플레이어 폴링 시점(약 2초 뒤)에 재시도한다. 3회 연속 실패하면 해당 URL은 포기하고 아트 없이 표시한다.

## 4.7 단일 세션 통신 흐름

```
호스트                                   덱
  │── TCP 연결 (7879) ──────────────────▶│
  │◀─ 핸드셰이크: 상호 공개키 교환 ──────▶│
  │  페어링된 덱 키인지 확인              │
  │  아니면 아무것도 안 보내고 연결 종료  │
  │── hello {caps: 허용 권한} ──────────▶│  페어링된 호스트 키인지 확인
  │◀── hello {status: "paired", addrs} ──│  아니면 denied 전송 후 연결 종료
  │◀── watch {구독 메트릭 목록} ──────────│  리소스 미터 위젯이 선택한 메트릭
  │── media, commands, metrics ────────▶│  허용된 항목만 전송. UI로 전달
  │── command_value, metric_values ────▶│  값이 바뀔 때마다 푸시
  │◀── action {id, name} ────────────────│  화면 버튼 탭 / 노브 조작
  │  권한 검사 → 실행 또는 거절           │
  │── result {id, ok, error} ──────────▶│
  │── media (변경된 상태) ──────────────▶│
  │── caps {변경된 권한} ───────────────▶│  PC 사용자가 연결 중 권한 변경
  │◀─ ping (0.5초 간격, 양방향) ────────▶│
```

- **생존 확인**: 양쪽이 0.5초마다 `ping`을 전송한다. 2초 동안 아무 메시지도 오지 않으면 연결이 끊긴 것으로 간주하고 종료한다.
- **동일 호스트 재접속 시** 덱은 기존 세션을 닫고 새 세션으로 교체한다. 다른 네트워크 경로로 붙더라도 공개키가 같으면 동일 호스트로 취급한다.
- **상태는 변경 이벤트가 발생했을 때만 전송한다.** 주기적으로 동일 상태를 재전송하지 않는다. 상태 종류별 트리거 조건은 아래와 같다:

  | 상태 | 전송 시점 | 호스트 감지 방식 |
  |---|---|---|
  | 재생 정보(`media`) | 곡 변경, 재생/일시정지, 시크, 플레이어 생성/종료 | 플레이어 이벤트 수신 + 2초 주기 폴링 |
  | 앨범 아트(`blob`) | 아트가 바뀔 때 1회 | 재생 정보의 아트 URL |
  | 명령 목록(`commands`) | 목록 또는 권한 변경 시 | 설정 파일 변경을 0.5초마다 감지 |
  | 스위치·노브 값(`command_value`) | 값이 바뀔 때 | 등록된 상태 조회 커맨드를 설정 주기(기본 2초)마다 실행 |
  | 리소스 수치(`metric_values`) | 덱 구독 항목 중 값이 바뀔 때 | 1초마다 측정(덱이 구독 중인 항목만) |
  | 허용 권한(`caps`) | 권한 변경 시 | 설정 파일 및 관리형 설정 변경을 0.5초마다 감지 |

- **재생 중 경과 시간 증가는 이벤트로 취급하지 않는다.** 덱이 로컬에서 자체 계산하므로 한 곡을 듣는 동안 `media`는 최초 1회만 전송된다.
- **"변경 여부"는 호스트가 판단한다**(`media::changed`): 덱이 현재 표시 중일 것으로 추정되는 위치(마지막 전송값 + 경과 시간)와 실제 플레이어 위치를 비교한다. 위치 외 다른 필드가 바뀌었으면 전송하고, 위치만 다르면 1.5초를 초과해 어긋났을 때만 전송한다(시크 발생).
- **호스트가 플레이어를 조회하는 시점**: 플레이어 변경 알림 수신 시(리눅스 D-Bus 신호: 프로퍼티 변경, 시크, 플레이어 추가/제거)와 2초 주기 폴링. 주기 폴링은 시크 이벤트를 따로 쏘지 않는 플레이어 대응용이다. 조회는 PC 로컬 동작이며 변화가 없으면 덱으로 아무것도 보내지 않는다.
- 덱이 액션을 요청한 직후에도 즉시 재조회해 결과를 바로 UI에 반영한다.
- **재생 위치를 보고하지 않는 플레이어**(항상 같은 값 반환)는 `rate`를 0으로 보낸다. 덱이 타이머를 돌리면 폴링 때마다 1.5초를 초과해 어긋나 원복되는 현상이 반복되기 때문이다.
- **덱 측 처리**: 데몬은 `media` 수신 시각을 기록해 두고 UI에 전달할 때마다 해당 시점 위치로 보정해 넘긴다(UI가 나중에 접속해도 정확한 위치를 받음). UI(미디어 위젯)는 수신한 위치에서 0.25초마다 자체 카운트한다.
- 덱 UI는 호스트가 새 상태를 보내 줄 때만 갱신된다. 버튼을 눌렀다고 UI가 선반영하지 않는다.
- 연결이 끊기면 덱은 해당 호스트의 런타임 상태(`media`, `caps`, 연결 경로, 명령 목록·값, 메트릭 목록·값)를 비우고 오프라인으로 표시한다.

## 4.8 연결 경로 및 장애 복구

- 덱은 `hello`에 자신의 IP 주소 목록을 실어 보낸다(USB, 이더넷, Wi-Fi 순). 호스트는 이 목록을 저장한다. 덱 부팅 직후 아직 DHCP 주소를 못 받은 상황을 대비해 이전에 알던 주소도 함께 유지한다(최대 8개). 마지막으로 연결 성공한 주소를 맨 앞에 두며, 덱이 보낸 목록 중 유효한 IP 주소만 수락한다.
- 호스트는 **USB 주소(`172.16.42.1`)부터** 순서대로 접속을 시도한다. 그다음은 저장된 주소 목록 순이다. 단일 접속 시도는 최대 1.5초 대기한다. 페어링된 덱이 없으면 접속 시도를 하지 않는다.
- 활성 연결이 끊기면(2초 내에 감지) 처음 경로(USB)부터 다시 순회하며 재접속을 시도한다. 모든 주소가 실패하면 1초 간격으로 재시도한다.
- 해당 주소에 페어링되지 않은 덱(또는 다른 서비스)이 응답하면 아무것도 보내지 않고 건너뛴다. TCP는 붙었으나 세션 수립에 실패하면(프로토콜 버전 불일치, `hello` 무응답 등) 해당 주소와 사유를 호스트 로그에 1회 남기고 다음 주소로 넘어간다.
- 덱은 호스트가 들어온 소켓 로컬 주소 인터페이스로 연결 경로(`usb`, `lan`, `wlan`)를 판별한다. UI 표시용으로만 사용한다.
- 검증 사례: USB 연결 상태에서 덱의 USB 네트워크를 내리자 호스트가 이더넷 IP로 재접속했고 덱은 동일 호스트로 인식했다(단절 후 재연결까지 약 4초).
- **대기 링크를 미리 열어 두지는 않는다.** 따라서 경로 전환에 수 초가 걸린다. 다중 경로를 동시에 열어 두고 즉시 페일오버하는 기능은 아직 없다.
- **LAN에서 mDNS 등으로 덱을 자동 탐색하지는 않는다.** LAN IP를 직접 지정하거나(`toss-connector pair --deck <IP>`), USB로 1회 연결해 주소를 받아 둬야 한다.

## 4.9 영속 데이터 저장 위치

| 항목 | 덱 | 호스트 |
|---|---|---|
| 디렉터리 | `/data/toss/` (데몬 사용자 전용 권한) | 설정 디렉터리 |
| 자기 키 | `key` | `key` |
| 페어링 목록 | `hosts.json` | `decks.json` |

- 덱의 `/data`는 재플래싱 후에도 유지되는 영구 파티션이다([03-userland-guide.md](03-userland-guide.md) 3.15절 "기기에만 남는 데이터"). 루트 이미지를 다시 구워도 덱 키와 페어링 목록이 남는다. 덱은 파일들을 원자적으로 기록하고(임시 파일 쓰기 + fsync + rename), 손상된 파일은 덮어쓰지 않고 `.bad` 접미사를 붙여 백업한다(`hosts.json.bad`, `key.bad`): 페어링 목록이 손상되면 빈 목록으로, 키가 손상되면 새 키로 시작한다(새 키가 생성되면 호스트 입장에서는 다른 기기이므로 재페어링 필요).
- 호스트 설정 디렉터리: 리눅스 `~/.config/toss-connector`(`$XDG_CONFIG_HOME` 준수), Windows `%APPDATA%\toss-connector`, macOS `~/Library/Application Support/toss-connector`. `--config <디렉터리>`로 재정의 가능하다. 없으면 소유자 전용 권한(0700)으로 생성하며, 이미 있는 디렉터리 권한은 건드리지 않는다.
- `key`: 2줄(비밀키, 공개키. 16진수). 소유자만 읽을 수 있게 생성한다. **비밀키가 들어 있으므로 외부에 공유하지 않는다.** 삭제하면 새 키가 발급되며 상대 기기에서는 다른 호스트로 인식되므로 재페어링해야 한다.

**덱의 `hosts.json`** — 호스트 키, 이름, OS.

```json
[{ "key": "87a6c85e…", "name": "my-pc", "os": "linux" }]
```

**호스트의 `key`** — 16진수로 인코딩된 32바이트 키 2줄 형식이어야 한다. 형식이 어긋나거나 읽을 수 없으면 원인을 출력하고 종료한다(새 키로 덮어쓰지 않음). 키가 필요한 동작(인자 없이 실행, `pair`, `sleep`, 웹 콘솔의 페어링·절전)을 처음 수행할 때 생성된다. `key`와 `console-token`은 다른 사용자 읽기 권한이 열려 있으면 실행 시마다 소유자 전용(0600)으로 보정한다.

**호스트의 `commands.json`** — 등록된 명령 정의(ID, 이름, 종류, 실행 커맨드들, 범위, 상태 조회 커맨드와 주기). 덱별이 아니라 호스트 단위 설정이다. `kind`가 생략된 항목은 `run`으로 간주한다. 수동 편집이 가능한 파일이므로 읽을 때마다 항목별로 검증한다: 잘못된 항목(역전된 범위, 미지원 종류, 허용 범위 초과 주기, ID 누락 또는 영숫자·`-`·`_` 1~64자 규칙 위반)은 무시하고 로그에 1회 경고만 남긴다. 파일에서 자동 삭제하지는 않는다.

```json
[{ "id": "c6dd2e6b", "name": "Terminal", "run": "foot" }]
```

**호스트의 `console.json`, `console-token`** — 웹 콘솔 포트 및 허용 Origin 설정, 그리고 인증 토큰(소유자 전용 읽기 권한. 삭제 시 재발급되며 기존 콘솔 탭은 새 토큰을 입력해야 함).

**호스트의 `lock`** — 실행 중인 `toss-connector`가 파일 락을 잡는 빈 파일. 동일 설정 디렉터리에서 중복 실행을 방지한다.

**호스트의 `/etc/toss-connector/managed.json`** — 설정 디렉터리 외부에 두는 시스템 관리형 권한·명령 설정(읽기 전용, NixOS 모듈이 생성). 없으면 관리형 설정이 비활성 상태로 동작한다. 환경 변수 `TOSS_CONNECTOR_MANAGED`로 경로를 지정할 수 있다(빈 문자열이면 무시).

**호스트의 `decks.json`** — 덱 키, 이름, 알려진 IP 목록, 웨이크업 주소(`wake`: 덱 Wi-Fi MAC), 사용자 지정 권한 맵. IP 목록은 마지막 연결 성공 주소가 맨 앞에 오며 최대 8개까지 보관한다. 덱이 보낸 목록 중 유효한 IP 주소만 수락한다(호스트명이나 포트가 포함된 문자열은 폐기). 덱 이름은 64자로 자르고, 웨이크업 주소는 MAC 형식일 때만 수락한다.

```json
[{
  "key": "a1b2c3d4…",
  "name": "toss-front",
  "addrs": ["172.16.42.1", "192.168.0.20"],
  "perms": { "media.control": false }
}]
```

- `perms`에 없는 권한은 기본값을 따른다. 사용자가 바꾼 항목이 없으면 `perms` 키 자체를 기록하지 않는다.
- 호스트의 `decks.json`, `commands.json`, `console.json`은 실행 중인 `toss-connector`, 다른 터미널 CLI(`allow`, `deny`, `command add` 등), 웹 콘솔이 동시에 접근할 수 있다. 수정 시에는 옆의 락 파일(`decks.json.lock` 등)에 파일 락을 걸고, 최신 내용을 다시 읽어 해당 항목만 수정한 뒤, 임시 파일(`<이름>.<PID>-<seq>.new`)에 쓰고 rename으로 교체한다(불완전한 파일이 남지 않고 동시 수정 시 경쟁 유실도 없음). 새로 쓰는 파일은 0600 권한으로 생성한다.
- **파싱할 수 없는 파일(수동 편집 중 깨진 JSON 등)은 덮어쓰지 않는다.** 해당 파일을 수정하는 동작(페어링, `forget`, `allow`, `command add`, `console allow` 등)은 사유를 출력하고 실패하며 로그에도 1회 남긴다. 복구되거나 삭제되기 전까지: `decks.json`이 깨졌으면 페어링된 덱이 없는 것으로 취급해 모든 권한을 차단한다(연결 중인 세션은 끊지 않고 권한만 모두 비활성화하며, 복구되면 정상 동작). `commands.json`이 깨졌으면 사용자 등록 명령이 없는 것으로 취급한다. `console.json`이 깨졌으면 기본값(포트 7880, 허용 Origin 없음)으로 동작한다. 빈 파일은 없는 파일과 동일하게 취급한다.
- 실행 중인 `toss-connector`는 파일 변경 여부를 mtime, 크기, inode 세 가지로 감시한다(같은 초 안에 두 번 수정돼도 놓치지 않음).

## 4.10 호스트 커넥터 `toss-connector`

**로그인한 사용자 세션에서** 실행해야 한다(미디어 플레이어는 사용자 세션 D-Bus에 뜨기 때문에 시스템 서비스에서는 보이지 않음).

```bash
nix build .#toss-connector -o dist/toss-connector && ./dist/toss-connector/bin/toss-connector
```

개발 중에는 `cd src/app/host && nix develop -c cargo run`. NixOS에서는 모듈로 설치해 사용자 서비스로 자동 실행한다(아래 "NixOS에 설치" 참고).

| 명령어 | 동작 |
|---|---|
| `toss-connector` | 페어링된 덱에 접속해 서비스 동작. 끊기면 자동 재연결 |
| `toss-connector pair [--deck 주소]` | 덱과 페어링. 주소 생략 시 USB 주소(`172.16.42.1`). 실패 시 사유 안내: 접속 불가(주소 포함), 덱이 페어링 모드 아님, 프로토콜 버전 불일치, 페어링 시간 초과 |
| `toss-connector list` | 페어링된 덱 목록 (키 접두사, 이름, 알려진 IP) |
| `toss-connector forget <키 접두사>` | 페어링 삭제 |
| `toss-connector trust [덱]` | 덱별 허용 권한 조회 |
| `toss-connector allow [덱] <권한>…` / `deny [덱] <권한>…` | 권한 허용 또는 거부. 실행 중인 `toss-connector`에 곧 반영 |
| `toss-connector sleep [덱]` | 덱을 절전 모드로 전환. 덱이 Wi-Fi에 연결된 상태에서만 동작 |
| `toss-connector wake [덱]` | 절전 중인 덱 웨이크업: 덱 Wi-Fi MAC을 담은 매직 패킷을 네트워크로 송신하고, 덱이 다시 접속을 받는지 최대 20초 확인 |
| `toss-connector command list` / `add <이름> -- <명령…>` / `remove <id 또는 이름>` / `run <id 또는 이름>` | 덱의 명령 버튼이 실행할 수 있는 명령 등록·삭제. `run`은 PC에서 바로 테스트 실행 |
| `toss-connector command add-switch <이름> --on <명령> --off <명령> [--state <명령>] [--every <초>]` | 스위치 등록 |
| `toss-connector command add-stepped <이름> --step <단계[=명령]>… [--set <명령>] [--state <명령>] [--every <초>]` | 단계 등록(2~12개). 단계별 커맨드를 지정하거나, 이름만 적고 `--set`의 `{}` 자리에 단계 이름이 들어가게 함 |
| `toss-connector command add-linear <이름> --set <명령> [--min 0] [--max 100] [--step 1] [--state <명령>] [--every <초>]` | 범위 등록. `--set`의 `{}` 자리에 값이 들어감 |
| `toss-connector command set <id 또는 이름> <값>` / `state <id 또는 이름>` | PC에서 값 설정 테스트, 현재 상태 조회 테스트(등록한 커맨드가 맞는지 확인할 때). `set`은 해당 명령의 커맨드만 실행: 스폰에 실패하거나 커맨드가 실패로 끝나면 사유를 출력하고 종료 코드 1로 종료. 상태 조회 커맨드가 있으면 설정한 값이 보일 때까지 최대 4초 동안 조회한 뒤 현재 상태를 출력 |
| `toss-connector managed` | 관리형 설정(NixOS 모듈의 `config`) 조회: strict 여부, 고정된 권한과 명령 |
| `toss-connector managed check <파일>` | 관리형 설정 파일을 검증하고 정리한 결과를 출력(모듈이 빌드 중에 사용. 오류가 있으면 실패) |
| `toss-connector console` | 웹 콘솔을 브라우저로 열기(실행 중인 `toss-connector`가 서빙) |
| `toss-connector console url` / `token` | 콘솔 URL(토큰 포함) / 토큰만 출력 |
| `toss-connector console allow <출처>` / `toss-connector console deny <출처>` | 외부에 호스팅한 콘솔 페이지의 Origin 허용 / 해제 |
| `toss-connector console list` | 콘솔 URL과 허용 Origin 목록 출력 |
| `toss-connector console port <번호>` | 콘솔 포트 변경(기본 7880. 재시작 필요) |
| `--config <디렉터리>` | 키와 설정 파일을 저장할 경로 |
| `--no-console` | 웹 콘솔 비활성화 (인자 없이 실행할 때만 사용) |

- 명령어가 받지 않는 인자가 있으면 실행하지 않고 사용법을 출력한다: 잉여 인자(`pair 10.0.0.7`처럼 — 주소는 `--deck` 뒤에 적는다), `pair`가 아닌 명령어의 `--deck`, 명령어와 함께 쓴 `--no-console`, `command add`가 아닌 곳의 `--` 뒤 커맨드.
- 종료 코드: 성공 0, 실패 1, 사용법 오류 2, 같은 설정 디렉터리로 이미 실행 중이면 3.
- 키(`key`)는 키가 필요한 명령어(인자 없이 실행, `pair`, `sleep`)만 읽고 생성한다. `list`, `trust`, `command …` 같은 명령어는 키를 생성하지 않는다.

### NixOS에 설치 (`programs.toss-connector`)

이 저장소의 flake가 `toss-connector` 패키지와 NixOS 모듈을 제공한다. 시스템 flake에 입력으로 추가하고 옵션을 켜면 설치되며 로그인 시 자동 실행된다.

```nix
# 시스템의 flake.nix
{
  inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
  inputs.toss-front.url = "git+file:///home/<사용자>/development/toss-front";   # 이 저장소가 있는 곳 (GitHub에서 가져오려면 "github:RFLXN/touch-oriented-stream-shell")

  outputs = { nixpkgs, toss-front, ... }: {
    nixosConfigurations.<이름> = nixpkgs.lib.nixosSystem {
      modules = [
        toss-front.nixosModules.default
        ./configuration.nix
      ];
    };
  };
}
```

```nix
# configuration.nix
{
  programs.toss-connector.enable = true;
}
```

| 옵션 | 기본값 | 의미 |
|---|---|---|
| `programs.toss-connector.enable` | `false` | `toss-connector`를 설치하고 사용자 서비스로 등록 |
| `programs.toss-connector.package` | 이 flake의 `packages.<시스템>.toss-connector` | 사용할 패키지 |
| `programs.toss-connector.autostart` | `true` | 로그인 시 자동 실행. 끄면 설치만 함 |
| `programs.toss-connector.target` | `"graphical-session.target"` | 함께 시작할 사용자 타깃. 해당 타깃을 활성화하지 않는 창 관리자를 쓰면 `"default.target"` |
| `programs.toss-connector.console.enable` | `true` | 웹 콘솔 활성화. 끄면 `--no-console` |
| `programs.toss-connector.path` | `[ ]` | 등록된 명령이 사용할 프로그램을 서비스 PATH 앞에 추가 |
| `programs.toss-connector.config` | `null` | 덱에 허용할 권한과 등록할 명령을 여기서 지정(아래 "NixOS에서 권한·명령 고정") |
| `programs.toss-connector.extraArgs` | `[ ]` | `toss-connector`에 추가로 전달할 인자. 원문 그대로 전달된다(`%`나 `$`를 systemd가 확장하지 않게 기록됨) |

- **사용자 서비스다**(`systemd --user`의 `toss-connector.service`). 시스템 서비스가 아니다: 미디어 플레이어와 등록된 명령은 로그인한 사용자의 세션에 속한다. 상태와 로그는 `systemctl --user status toss-connector`, `journalctl --user -u toss-connector`로 확인한다. 시스템 사용자(로그인 화면을 띄우는 사용자 등)의 세션에서는 실행되지 않는다(`ConditionUser=!@system`).
- **비정상 종료 시 3초 뒤 재시작한다. 재시작해도 소용없는 두 경우는 재시작하지 않는다**(`RestartPreventExitStatus=2 3`): 인자 오류로 종료된 경우(종료 코드 2 — `extraArgs`를 잘못 적었을 때)와 이미 실행 중인 인스턴스가 있어 종료된 경우(종료 코드 3 — 아래).
- **등록된 명령이 프로그램을 찾는 경로**: 서비스 PATH를 로그인 셸과 비슷하게 구성한다 — `/run/wrappers/bin`, 사용자 프로필(`~/.nix-profile`, `/etc/profiles/per-user/<사용자>`), 시스템(`/run/current-system/sw/bin`). 터미널에서 되는 커맨드가 덱에서 안 되면 대개 PATH 문제다: `programs.toss-connector.path`에 해당 패키지를 넣거나 커맨드에 전체 경로를 적는다.
- **창을 띄우는 명령**은 세션 환경 변수(`WAYLAND_DISPLAY` 등)가 사용자 서비스에 전달돼 있어야 한다. 데스크톱 환경은 이를 전달해 준다. 그래서 기본값이 그래픽 세션 시작 이후(`graphical-session.target`)다.
- **같은 설정 디렉터리로는 단일 인스턴스만 실행된다.** 둘이 실행되면 같은 키로 접속해 덱이 앞선 세션을 끊으므로 둘이 번갈아 끊기고 붙는다. 그래서 `toss-connector`는 설정 디렉터리의 `lock`에 파일 락을 잡고, 이미 실행 중인 인스턴스가 있으면 종료한다(종료 코드 3. 서비스는 이 코드로 종료된 경우 재시작하지 않는다). 수동으로 실행해 둔 인스턴스가 있으면 서비스가 뜨지 않으므로, 서비스를 쓰려면 수동 실행을 종료한다. `--config`로 다른 디렉터리를 쓰는 인스턴스는 키도 달라 별개로 실행된다. `lock`을 열거나 잠글 수 없으면(파일 락을 지원하지 않는 파일시스템 등) 그 사실을 로그에 남기고 그대로 실행한다.
- **권한과 명령은 사용자가 관리한다 — 모듈에서 고정하지 않는 한.** 기본적으로 각 사용자의 `~/.config/toss-connector`에 저장되며(4.9절) CLI나 웹 콘솔로 수정한다. 모듈에서 고정해 잠글 수도 있다(아래 "NixOS에서 권한·명령 고정"). 키, 페어링, 콘솔 토큰은 항상 사용자 소유다.
- **입력 URL**: `git+file://…`은 git이 추적하는 파일만 가져간다(백업이나 빌드 결과물은 포함되지 않는다). `path:…`로 넣으면 디렉터리 전체가 Nix 스토어로 복사되므로 쓰지 않는다. **커밋이 없는 저장소는 잠글 수 없어서**(`flake.lock`에 기록할 리비전이 없다) 경고가 나오고 락 파일이 기록되지 않는다 — 커밋한 뒤에 사용한다.
- 패키지는 이 저장소가 고정한 Rust 툴체인으로 빌드된다(사용하는 쪽의 nixpkgs와 무관하게 같은 결과물이 나온다). 빌드 도중 테스트를 실행한다. `x86_64-linux`와 `aarch64-linux`를 제공한다. `pkgs.toss-connector`로 쓰려면 `overlays.default`를 적용한다.
- 관련 코드: `nix/toss-connector.nix`(패키지), `nix/nixos-module.nix`(모듈), `nix/module-check.nix`(모듈 검사), `flake.nix`(출력). `nix flake check`가 이 검사를 실행한다: 모듈을 활성화한 NixOS를 평가해 생성되는 서비스 유닛 구조(실행 파일, PATH, 타깃, 재시작 규칙, 시스템 사용자 제외, 인자가 원문 그대로 기록되는지)를 검증한다.

### NixOS에서 권한·명령 고정 (`programs.toss-connector.config`)

덱에 허용할 권한과 등록할 명령을 NixOS 설정에 선언해 둘 수 있다. 선언한 항목은 CLI나 웹 콘솔에서 바꿀 수 없다.

```nix
programs.toss-connector = {
  enable = true;
  config = {
    strict = true;        # 기본값
    permissions = [ "media.info" "media.control" "command.run" ];
    commands = [
      { name = "Terminal"; run = "foot"; }
      { name = "Mic"; kind = "switch";
        on = "wpctl set-mute @DEFAULT_SOURCE@ 0"; off = "wpctl set-mute @DEFAULT_SOURCE@ 1";
        state = "! wpctl get-volume @DEFAULT_SOURCE@ | grep -q MUTED"; }
      { name = "Profile"; kind = "stepped"; steps = [ "power-saver" "balanced" "performance" ];
        set = "powerprofilesctl set {}"; state = "powerprofilesctl get"; }
      { name = "Volume"; kind = "linear"; max = 100; step = 5;
        set = "wpctl set-volume @DEFAULT_SINK@ {}%"; }
    ];
  };
};
```

| 항목 | `strict = true` (기본값) | `strict = false` |
|---|---|---|
| 권한 | **명시된 권한만 허용된다.** 나머지는 거부되며 덱별로 바꿀 수 없음 | 명시된 권한은 허용 상태로 **해제 불가.** 명시되지 않은 권한은 사용자가 덱별로 설정 |
| 명령 | **명시된 명령만 제공된다.** 기존 사용자 명령은 무시되며 추가 등록 불가 | 명시된 명령은 **수정·삭제 불가.** 사용자가 별도 명령 추가 등록 가능 |
| CLI·웹 콘솔 | 권한과 명령 변경 불가(조회와 실행 테스트는 가능) | 명시된 항목만 잠기고 나머지는 기존처럼 수정 가능 |

- **`config`가 `null`(기본값)이면 관리형 강제가 없다.** 모든 권한과 명령을 사용자가 직접 관리한다(모듈만 활성화한 상태).
- **권한은 페어링된 모든 덱에 일괄 적용된다.** 덱별 차등 지정은 없다. 덱은 PC에서 사용자가 검증 코드를 확인해야만 페어링되므로, strict 모드에서도 새 덱을 페어링하면 명시된 권한이 그대로 부여된다.
- **명령 ID(`id`)**: 덱 위젯은 ID로 명령을 참조한다. 생략하면 이름에서 파생된다(같은 이름이면 항상 같은 ID). 따라서 이름을 바꾸면 ID도 바뀌어 기존 위젯을 다시 배치해야 한다. 이름을 바꿔도 위젯 연결을 유지하거나 기존 수동 등록 명령을 이관하려면 `id = "585f6b9d";`처럼 기존 ID를 명시하면 된다(`toss-connector command list`에서 확인 가능).
- **빌드 타임 검증.** 알 수 없는 권한명, 잘못된 필드(명령이나 단계 내부 오타 포함), 유효하지 않은 명령 정의(빈 커맨드, 역전된 범위 등), 중복 ID·이름이 있으면 `nixos-rebuild` 단계에서 원인과 함께 실패한다. 검증은 `toss-connector managed check <파일>`이 수행한다.
- **저장 경로**: `/etc/toss-connector/managed.json`(읽기 전용, Nix 스토어 링크). 사용자 설정(`~/.config/toss-connector`의 `decks.json`, `commands.json`)과는 분리돼 있으며 런타임에 `toss-connector`가 둘을 병합한다. "설정을 잠근다"는 것은 사용자 파일 쓰기를 막는 것이 아니라 잠긴 영역에 대해 프로그램이 사용자 파일을 무시하거나 수정을 거부한다는 뜻이다. 사용자가 `decks.json`을 수동 편집해 권한을 켜도 반영되지 않는다.
- **운용 데이터는 잠기지 않는다**: 키, 페어링 목록, 덱 IP, 콘솔 토큰·허용 Origin. strict 모드에서도 페어링 추가와 해제는 가능하다.
- **반영**: 실행 중인 `toss-connector`가 파일 변경을 감지해 곧 반영한다(`nixos-rebuild switch` 후 재시작 불필요). 변경된 권한과 명령 목록은 덱에도 푸시된다.
- **조회 방법**: `toss-connector managed`로 현재 적용된 관리형 설정을 확인한다. `toss-connector trust`, `command list`, 웹 콘솔에서는 잠긴 항목에 `Nix` 태그가 붙는다.
- 손상되거나 읽을 수 없는 파일이 놓이면 **전체 거부 strict 모드로 폴백한다**(설정 파일이 깨졌다고 잠금이 풀리는 것을 방지). 빌드 시 검증을 거치므로 정상 환경에서는 발생하지 않으며, 실패 시 로그에 1회 경고를 남긴다(복구 후 다시 깨지면 재기록).
- 시스템 전역(`/etc`) 설정이므로 해당 PC의 모든 사용자에게 동일하게 적용된다.
- 관련 코드: `src/app/host/src/managed.rs`(파싱, 검증, 병합 규칙), `nix/nixos-module.nix`(모듈 옵션 및 JSON 생성).

### 웹 콘솔

CLI 기능을 브라우저에서 제공한다: 덱별 권한 토글, 명령 등록·수정·삭제 및 테스트 실행, 페어링(코드 확인), 절전·웨이크업. 실행 중인 `toss-connector` 프로세스 내부에서 서빙되므로 별도 프로세스가 필요 없다.

```bash
toss-connector                 # 실행해 두면 콘솔도 함께 기동 (http://127.0.0.1:7880/)
toss-connector console         # 브라우저로 열기 (토큰 자동 첨부)
```

**프론트엔드는 정적 파일 묶음이다**(`src/app/host/console/`의 `index.html`, `app.js`, `style.css`. 프레임워크나 빌드 단계 없음). 서빙 방식은 두 가지 중 하나다.

| | 기본 | 선택 |
|---|---|---|
| 제공 방식 | `toss-connector` 자체 서빙 (`http://127.0.0.1:7880/`. 바이너리에 내장) | 외부에 호스팅한 동일 정적 파일 (GitHub Pages 등) |
| 사용법 | `toss-connector console` | PC에서 `toss-connector console allow <출처>` 실행 후 페이지 "연결" 입력란에 로컬 주소와 토큰 입력. 주소는 로컬호스트만 허용(`http://127.0.0.1:<포트>` 또는 `http://localhost:<포트>`) |
| 신뢰 대상 | 직접 빌드한 `toss-connector` | **해당 외부 URL에 배포된 파일** |

**이 API를 호출할 수 있으면 PC에서 임의의 명령을 등록·실행할 수 있다.** 반면 브라우저는 아무 웹 페이지에서나 `127.0.0.1`로 요청을 날릴 수 있다. 이를 막기 위해 4중 방어선을 둔다.

| | 방어 수단 | 차단 대상 |
|---|---|---|
| 1 | `127.0.0.1` 루프백 바인딩 | 외부 네트워크 호스트의 접속 |
| 2 | **Bearer 토큰**: `/api/` 모든 요청에 `Authorization: Bearer <토큰>` 필수. 토큰은 설정 디렉터리 `console-token`에 소유자 전용(0600)으로 저장 | 토큰을 모르는 로컬 프로세스 및 웹 페이지 |
| 3 | **Origin 검증**: 요청에 `Origin` 헤더가 있으면 콘솔 자체 Origin 또는 허용 목록과 일치해야 함. 와일드카드 허용 없음. `null` Origin도 거부 | 사용자가 열어 둔 다른 웹사이트. 미허용 Origin에는 CORS 헤더를 내려주지 않아 브라우저가 요청 자체를 막음 |
| 4 | **Host 헤더 검증**: 요청의 `Host`가 `127.0.0.1:<포트>` 또는 `localhost:<포트>`여야 함 | DNS 리바인딩(외부 도메인을 `127.0.0.1`로 가리켜 동일 출처로 위장하는 공격) |

- **Origin 허용 목록은 CLI로만 수정한다.** HTTP API 엔드포인트가 없다. 콘솔 UI에서는 현재 허용 목록 조회만 가능하다.
- **외부 호스팅 페이지 허용은 해당 코드에 PC 명령 실행 권한을 위임하는 것과 같다.** 해당 저장소나 계정을 수정할 수 있는 주체가 PC에서 명령을 실행할 수 있게 되므로, 기본값인 `toss-connector` 내장 서빙을 권장한다.
- 토큰은 `toss-connector console` 실행 시 URL 프래그먼트(`#token=…`)에 붙여 브라우저로 넘긴다. 프래그먼트는 서버로 전송되지 않으며, 프론트엔드가 로드 직후 주소창에서 지우고 `localStorage`에 저장한다.
- `toss-connector`가 서빙하는 콘솔 HTML에는 self-only CSP 헤더가 붙어 외부 스크립트 로드와 외부 데이터 전송을 차단한다.
- UI에 출력되는 동적 문자열(명령 이름, 커맨드 등)은 텍스트 노드로만 삽입해 HTML 인젝션을 방지한다.
- 콘솔 UI는 1.5초마다 상태를 폴링해 변경된 부분만 갱신한다. 콘솔에서 수정한 내용은 CLI와 같은 파일(`decks.json`, `commands.json`)에 기록되므로 실행 중인 `toss-connector`에 곧 반영된다(4.5절, 4.6절).
- 설정 파일은 `console.json`이다: `{"port": 7880, "origins": ["https://…"]}`. 콘솔을 끄려면 `toss-connector --no-console`로 실행한다.

| API | 동작 |
|---|---|
| `GET /api/state` | 전체 상태 스냅샷: 호스트 정보, 권한 테이블, 덱 목록(연결 상태, 권한), 명령 목록, 페어링 진행 상태, 허용 Origin 목록 |
| `POST /api/decks/<키>/perms` | `{"id": "command.run", "on": true}`. `on`이 `null`이면 기본값으로 복원 |
| `POST /api/decks/<키>/forget`, `sleep`, `wake` | 페어링 삭제, 절전 진입, 웨이크업(최대 20초 대기) |
| `POST /api/commands`, `PUT`·`DELETE /api/commands/<id>` | 명령 등록, 수정(ID 유지), 삭제 |
| `POST /api/commands/<id>/run`, `set`, `GET …/state` | PC에서 즉시 실행, 값 설정 테스트, 현재 상태 조회 |
| `POST /api/pair`, `/api/pair/confirm`, `/api/pair/cancel` | 페어링 시작(`{"addr": …}`), 검증 코드 확인, 취소. 진행 상태는 `/api/state`의 `pairing`으로 확인 |

실패 시 `{"error": "사유"}`와 함께 4xx/5xx 상태 코드를 반환한다: 토큰 불일치 401, Host/Origin 검증 실패 403, 대상 덱/명령 없음 404, 요청 형식 오류 400, Nix 관리형 설정 충돌 409, 파일 I/O 또는 커맨드 실행 실패 500. `set`은 커맨드 실행이 실패로 끝나도 500을 반환한다. 정본은 `src/app/host/src/console.rs` 상단 주석에 있다.

웹 콘솔에서 진행하는 페어링도 CLI `pair`와 동일한 상태 머신(`src/app/host/src/pairing.rs`)을 타므로, 사용자가 검증 코드를 확인하기 전에는 덱이 완료 신호를 보내도 저장하지 않는다.

### 참고 사항

- **절전과 웨이크업.** 덱 재우기는 덱 설정 UI와 PC(`toss-connector sleep`) 양쪽에서 가능하지만, 깨우기는 PC(`toss-connector wake`)에서만 가능하다.
  - 웨이크업 대상 주소(덱 Wi-Fi MAC)는 덱이 `hello`에 실어 보내며 호스트가 `decks.json`의 `wake`에 저장한다. 따라서 덱이 Wi-Fi에 연결된 채 깨어 있는 동안 최소 1회는 접속한 적이 있어야 한다.
  - 매직 패킷은 `255.255.255.255`, 덱 IP의 서브넷 브로드캐스트 주소(마지막 옥텟 255, /24 가정), 덱 IP 자체 세 곳으로 송신한다. **PC와 덱이 같은 네트워크(서브넷)에 있어야 한다.**
  - **덱은 Wi-Fi로 수신한 매직 패킷으로만 깨어난다.** 이더넷으로는 깨어나지 않는다(검증 완료). USB만 연결돼 있고 Wi-Fi가 없으면 깨울 수 없다.
  - `toss-connector sleep`은 별도 일회성 연결을 열어 요청한다. 상주 `toss-connector`가 그 덱에 연결 중이었다면 그 연결은 끊기는데, 덱이 슬립에 들어가면 어차피 끊긴다. 덱이 깨어나면 상주 프로세스가 자동으로 재연결한다.
- 미디어 플레이어는 MPRIS D-Bus 인터페이스를 지원하는 프로그램이면 모두 연동된다. 여러 플레이어가 떠 있으면 재생 중인 플레이어를 우선하며, 없으면 직전에 보던 플레이어를 유지한다. D-Bus 쿼리마다 0.8초 타임아웃을 적용해 응답 없는(행 걸린) 플레이어가 있어도 재생 정보와 덱이 요청한 액션이 그만큼 지연될 뿐 덱과의 세션은 끊기지 않는다(ping은 별도 스레드가 송신).
- 로그(`journalctl --user -u toss-connector`)에는 동일 주소에 대한 동일 사유를 1회만 출력한다: 미페어링 덱, 연결 거절, 세션 수립 실패(프로토콜 버전 불일치 시 양측 버전 포함). 해당 주소에 정상 연결됐다가 다시 문제가 발생하면 1회 재기록한다. 페어링된 덱이 없으면 접속 시도 자체를 하지 않는다.
- 상태 조회 커맨드(`--state`)는 3초 안에 종료돼야 한다. 타임아웃을 넘기면 해당 프로세스와 자식 프로세스 그룹 전체를 강제 종료하고 값을 알 수 없음(`null`)으로 처리한다. 프로세스 종료 후 백그라운드 자식이 stdout 파이프를 잡고 있어도 파이프 읽기 타임아웃 후 읽힌 출력만 쓰고 정리한다. 값 설정 커맨드(`--set`, `--on`, `--off`, 단계 커맨드)가 5초를 넘기면 대기를 중단하고 그대로 둔다(앱 실행용 커맨드일 수 있기 때문).
- 비리눅스 환경에서는 컴파일은 되지만 실행 가능한 기능이 없어 빈 권한 목록(`caps: []`)으로 접속한다.
- 현재는 한 번에 1대의 덱에만 접속한다.

## 4.11 덱 측 구현 (`tossd`와 UI)

덱 데몬은 호스트 연결(`7879`, 전체 인터페이스)과 UI 연결(`7878`, `127.0.0.1` 전용)을 별도 리스너로 처리한다. 호스트 관련해 데몬과 UI가 주고받는 IPC 메시지는 아래와 같다(전체 UI 프로토콜은 [03-userland-guide.md](03-userland-guide.md) 3.16절 참고).

| 방향 | 메시지 | 의미 |
|---|---|---|
| 데몬 → UI | `hosts` | 페어링된 호스트 목록 및 페어링 진행 상태. 변경 시만 전송 |
| 데몬 → UI | `meters` | 수집 가능한 메트릭 목록: 대상 → 목록. 대상은 `@deck`(덱 자신) 또는 호스트 ID. 변경 시 전체 전송 |
| 데몬 → UI | `meter_values` | 메트릭 현재 값: 대상 → 메트릭 ID → 값. 리소스 미터 위젯이 구독 중인 항목만 포함 |
| 데몬 → UI | `values` | 호스트에 등록된 스위치·노브 현재 값: 호스트 ID → 명령 ID → 값. 변경 시 전체 전송. 값을 모르는 항목은 미포함 (`hosts`와 분리 전송: 노브 조작 시 빈번히 바뀌는데 그때마다 앨범 아트가 포함된 `hosts` 전체를 재전송하지 않기 위함) |
| UI → 데몬 | `action` | 호스트 액션 실행 요청(`host`, `name`, `args`). `host`가 비어 있으면 연결된 첫 호스트로 라우팅. `widget`에 위젯 ID를 주면 결과가 `result`로 회신됨 |
| 데몬 → UI | `result` | 위젯 액션 실행 결과(`widget`, `seq`, `ok`, `error`). 그 액션을 받은 호스트의 응답만 전달. 전송 실패 시에도 회신됨(`ok` false, `error` `no_host`) |
| UI → 데몬 | `pair_start`, `pair_stop` | 페어링 모드 활성화·비활성화(중지 시 대기 중인 호스트에 `rejected` 전송) |
| UI → 데몬 | `pair_accept`, `pair_reject` | 페어링 요청 수락(`code`: 화면에 떠 있던 숫자. 현재 후보 코드와 다르면 데몬이 무시), 거절 |
| UI → 데몬 | `host_forget` | 페어링 삭제(`id`) |

**`hosts` 페이로드 구성**

| 필드 | 의미 |
|---|---|
| `hosts[]` | 페어링된 호스트별 정보: `id`(공개키), `name`, `os`, `caps`(덱에 허용된 권한), `via`(`usb`·`lan`·`wlan`), `connected`, `media`, `art`. 오프라인이면 `caps`와 `via`가 비고 `media`·`art`는 `null`. `name`, `os`, `caps`는 데몬이 정제한 값(4.4절) |
| `hosts[].media.position_ms` | **UI에 전달하는 시점 기준 위치.** 재생 중이면 UI가 여기서부터 `rate` 배속으로 카운트 |
| `hosts[].commands` | 해당 호스트에 등록된 명령 목록(`id`, `name`, `kind`, `steps`, `min`·`max`·`step`). 명령 위젯 추가 시 이 목록에서 고르며, 위젯은 자기 명령이 여기 존재할 때만 활성화됨. **0 값은 생략됨**(`min`이 0이면 필드 없음) |
| `hosts[].art` | 앨범 아트(`id`, `mime`, `data`: base64). `media.art`와 `id`가 일치하면 현재 곡의 앨범 아트. UI는 `data:` URI로 조립해 렌더링 |
| `pairing.active` | 페어링 모드 활성 여부 |
| `pairing.candidate` | 페어링 대기 중인 후보 호스트(없으면 `null`): `name`, `os`, `via`, `code`(검증 코드), `host_confirmed`, `deck_accepted` |

- 위젯은 `host`와 `action(name, args)`를 받는다(3.17절). 명령 위젯은 대상 명령(`command`)와 현재 값(`value`)도, 리소스 미터는 대상 메트릭 목록과 수치(`metrics`, `metricValues`)도 전달받는다.
- **덱이 표시 중인 메트릭을 호스트에 구독 요청한다(`watch`).** 데몬이 레이아웃 내 리소스 미터 위젯들이 고른 항목을 호스트별로 집계해(`Layout::watched`), 호스트 연결 시와 레이아웃 변경 시 전송한다. 덱 자체 리소스 위젯 항목은 데몬이 직접 측정한다.
- **스위치와 노브는 사용자 조작 결과를 낙관적으로 선표시한다.** 값을 설정한 뒤 1.5초 동안은 사용자가 선택한 값을 보여 주다가 이후 다시 호스트가 보고한 값으로 복귀한다. 그사이에 호스트가 새 값을 알려 오면 그대로 이어받고, 변화가 없으면(커맨드 실행 실패 등) 기존 값으로 돌아간다. 연속 노브는 드래그 중 0.09초 스로틀링으로 전송하고, 손을 뗄 때 최종값을 한 번 더 전송한다. **위젯은 `host.caps`를 확인해 미허용 액션을 호출하는 컨트롤을 비활성화한다.**
- **위젯마다 대상 호스트를 지정한다.** 위젯 설정 `host`에 호스트 ID가 지정돼 있으면 해당 호스트만 추적·제어한다(미연결 시 오프라인으로 표시). 비어 있으면 연결된 첫 호스트를 따른다. 추가 시 선택한다([03-userland-guide.md](03-userland-guide.md) 3.16절 "레이아웃 편집").
- 관련 코드(`src/app/tossd/src/hosts/`): `session.rs`(단일 세션 — 헬로, 수락 판정, 메시지 수신), `pairing.rs`(페어링 모드·후보·상호 확인), `blob.rs`(청크 기반 앨범 아트 조립), `store.rs`(`hosts.json`과 `key`), `mod.rs`(호스트 상태 `Hosts`, UI 전달 모델, 액션 라우팅). 변경 사항은 `Events`(`hosts`, `values`, `meters`, `result`, `sleep`)로 데몬 코어에 전달하며 `src/app/tossd/src/state.rs`의 `Shared`가 받아 UI로 푸시한다.
- 덱 측 로그는 `/var/log/tossd.log`의 `host:` 접두사 라인이다(페어링, 연결, 종료, 거절, 권한 변경, 액션 실패). 재생 정보 같은 상태 페이로드는 남기지 않는다.

## 4.12 확장 가이드

### 호스트에서 새 상태 추가 (예: 시스템 볼륨)

**이벤트 발생 시에만 전송하도록 설계한다.** 주기적인 전체 상태 재전송은 하지 않는다. 전송 판단은 호스트 측이 담당한다. 기존 구현 패턴을 참고하면 된다(4.7절 표):

- 시간에 따라 선형으로 변하는 값(재생 위치 등)은 "기준 시점 값 + 진행 속도"만 보내고 덱이 자체 계산하게 둔다.
- 대용량 바이너리는 `blob`으로 분리하고 상태 메시지에는 식별 ID만 싣는다.
- 자주 변하는 메트릭은 **덱이 구독한 항목만** 측정하고(`watch`), 표시 자릿수 기준으로 반올림해 달라진 값만 보낸다.
- 갱신 빈도가 높은 작은 값은 무거운 상태 객체와 메시지를 분리한다(스위치·노브 값, 메트릭 수치는 `hosts`와 별도 메시지로 UI 전달).

1. 프로토콜(`src/app/proto/src/lib.rs`)의 `HostMsg`에 새 메시지와 데이터 구조체를 추가한다.
2. **해당 데이터를 덱에 노출해도 되는지 제어하는 권한을 추가한다**(아래 "권한(capability) 추가" 참고).
3. 호스트(`src/app/host`): OS 종속 조회 로직을 트레이트 + OS별 모듈로 분리하고(`media.rs` 패턴), `src/session.rs`에 상태 피드를 추가한다(`MediaFeed`, `CommandFeed`, `MeterFeed` 구조 참고: 각 피드가 직전 전송값을 기억해 `poll` 시 변경분만 전송하고 `Session::turn`이 이를 호출).
4. 덱(`src/app/tossd/src/hosts/session.rs`): `serve`에서 수신해 `HostInfo`(`hosts/mod.rs`)에 반영하고, `Changed`를 반환하면 UI로 푸시된다. 갱신 빈도가 높은 값이면 `HostInfo`와 분리해 별도 채널로 전달한다(`Events`의 `values`, `meters` 방식).
5. UI: 위젯 QML에서 `host` 프로퍼티를 참조한다(분리 채널 값은 `shell/WidgetSlot`에서 바인딩해 전달).

### 덱에서 새 액션 추가 (예: 볼륨 조절)

1. 프로토콜에 `ACTION_*` 상수를 추가하고 **`action_cap`에 필요 권한을 매핑한다.** 매핑되지 않은 액션은 호스트가 차단한다.
2. 호스트: `src/session.rs`의 `Session::act`에서 권한 검증 후 해당 핸들러로 라우팅한다(현재 `command.*`는 `CommandFeed::act`, 나머지는 미디어 플레이어로 전달).
3. UI: 위젯에서 `action("이름", 인자)` 시그널을 발생시킨다. 덱 데몬은 수정할 필요 없이 이름과 인자를 그대로 호스트로 중계한다.

### 권한(capability) 추가

1. 프로토콜에 `CAP_*` 상수를 추가한다.
2. `src/app/host/src/trust.rs`의 `PERMISSIONS` 테이블에 항목을 추가한다(ID, 설명, 기본값). **PC 시스템을 변경하거나 제어하는 권한은 기본값을 거부로 둔다.**
3. `src/app/host/src/session.rs`의 `can` 계산 로직에 "현재 PC 환경에서 실제 실행 가능한지" 조건을 추가한다.
4. 덱 UI에서 해당 액션을 보내는 컨트롤이 `host.caps`를 보고 비활성화되도록 처리하고, `DevicePage`의 `capText`에 표시용 라벨을 추가한다.
5. 웹 콘솔, CLI, NixOS 모듈 검증(`permissions`)은 `PERMISSIONS` 테이블을 참조하므로 별도 수정이 필요 없다. 이 문서 4.5절 표와 `nix/nixos-module.nix` 옵션 설명에만 추가하면 된다.

### 신규 OS 지원 (Windows, macOS)

`src/app/host/src/media.rs`의 `open()`에 해당 OS용 백엔드를 추가한다. `MediaControl` 트레이트 메서드 3종(`poll`: 현재 재생 상태·아트 URL 조회, `action`: 제어 실행, `on_change`: 변경 알림 콜백 등록 — 알림 API가 없으면 빈 구현으로도 2초 폴링으로 동작)을 구현하면 된다. 변경 판정(`changed`)과 앨범 아트 리사이징 로직은 OS 무관 공용이다.

**설계 확정 사항 (2026-11-17)**

- 명령 실행은 "PC에 미리 등록된 명령만 노출하고 덱은 선택만 한다"는 모델을 유지한다. 덱이 보낸 raw 커맨드를 실행하는 구조는 두지 않는다(덱 침해 시 PC 임의 명령 실행 위험; 덱 SSH는 끌 수 있으나 켜진 상태에서는 LAN에 열려 있음).
- 상태 동기화는 이벤트 기반 푸시만 사용한다. 주기적으로 요청하거나 같은 상태를 재전송하는 방식은 쓰지 않는다(4.7절).
- 직렬화 포맷은 JSON을 유지한다.
- PC 설정 UI는 네이티브 데스크톱 앱이 아니라 정적 웹 콘솔로 제공한다. 기본은 `toss-connector` 내장 서빙이며, 외부 호스팅 페이지는 명시적 Origin 허용 목록으로만 연다. 와일드카드 Origin 허용은 두지 않는다.
- `toss-connector`는 동일 설정 디렉터리에서 단일 인스턴스만 실행한다.
- 설정 디렉터리 JSON 파일이 손상되면 덮어쓰지 않고, 복구될 때까지 안전한 기본 상태(페어링 덱 없음, 전체 거부)로 동작한다.

Nix 빌드 바이너리를 동일 서비스 조건(`systemd-run --user`, 동일 PATH)으로 실행 시 덱 연결·재생 정보 전송 동작, 등록한 명령이 홈 디렉터리에서 실행되고 `wpctl`·`xdg-open`을 PATH에서 탐색. 두 번째 인스턴스 실행 시 중복 실행 종료(코드 3) |
| NixOS 관리형 설정 | `nix flake check`: 모듈 `config` 지정 시 검증 통과한 `/etc/toss-connector/managed.json` 생성(ID 자동 파생 및 명시 ID 유지), 잘못된 설정(미지원 권한, 상태 커맨드 없는 주기 지정) 시 빌드 실패. 실기기 연동: 해당 파일 지정 실행 시 `strict = false`에서 고정 권한 거부 불가, 고정 명령 삭제·중복 이름 등록 차단, 사용자 명령 4개 정상 동작. `strict = true`로 변경하자 **재시작 없이** 고정 명령 1개만 남고 나머지 명령 위젯 흐려짐. 콘솔에 잠긴 항목별 `Nix` 태그 및 토글·수정·삭제 잠금. 파일 제거 후 재실행 시 기존 상태 복원 |

### 보안 및 운영 참고 사항

- 덱 SSH가 무비밀번호 상태로 LAN에 열려 있다는 기본 전제(공유기가 외부 인바운드를 차단)는 동일하다. 단 이제 덱 설정 UI에서 SSH를 끌 수 있다([03-userland-guide.md](03-userland-guide.md) 3.16절 "SSH 켜고 끄기"). 호스트 연동 보안(포트 `7879`)은 SSH와 독립적으로 동작한다.
- 덱의 USB 네트워크(`usb0`)를 `ip link set usb0 down`으로 내렸다가 다시 올리면 USB 통신이 복구되지 않는다(테스트 중 확인). 재부팅하면 복구되며, 케이블 탈착 시와 동일한지는 미확인 상태다.
- 덱이 모든 인터페이스에서 `7879` 포트를 열고 있으므로 같은 LAN의 누구나 TCP 접속을 시도할 수는 있다. 단 페어링 모드가 아니면 키 교환 직후 거절하고 연결을 닫는다. 페어링 모드 2분 동안에는 누구든 페어링 요청을 보낼 수 있으나, 덱 화면에서 사용자가 검증 코드를 확인하고 `ACCEPT`를 눌러야만 수락된다.

## 4.14 대안: 덱을 USB 키보드로 동작시키기 (미검증)

위 네트워크 방식과는 별개인 대안이다. 구현하거나 테스트하지는 않았다. 키 입력만 단방향으로 보낼 수 있고 PC 상태를 받아 올 수는 없으므로 위 프로토콜을 대체하지는 못한다.

기기가 PC에 표준 USB HID 키보드로 인식되게 하는 방식이다. PC에 어떤 소프트웨어도 설치할 필요가 없어 아무 PC에 꽂아도 바로 동작하며, 일반 스트림덱과 비슷한 사용감을 낸다.

- 커널에는 이미 HID 가젯 드라이버(`f_hid`)를 내장해 두었다.
- 현재 USB 가젯은 `src/os/initramfs/init`의 `setup_gadget()`이 구성한다(RNDIS + ACM). 여기에 HID function을 하나 더 추가하면 된다: `functions/hid.usb0`에 `protocol`, `subclass`, `report_length`, `report_desc`(키보드 리포트 디스크립터)를 설정하고 config에 심볼릭 링크로 묶는다.
- 구성이 끝나면 기기에 `/dev/hidg0` 노드가 생기며, 8바이트 키보드 리포트 패킷을 write하면 PC로 키 입력이 전달된다.
- 가젯 구성을 변경하면 USB 재열거가 일어나므로 SSH가 한 번 끊긴다. initramfs 수정 사항이므로 부트 이미지를 다시 플래싱해야 한다.

실기기에서 검증하지 않았으나 표준 리눅스 USB 가젯(configfs) 절차 그대로다.
